## 1. Overview & Core Principles

The **Time Agent (Proactive Schedule Monitoring Engine)** (Phase 13) provides deterministic, policy-driven temporal monitoring over activity baselines, actual progress calculations, evidence coverage, and schedule projections.

It enforces 6 fundamental temporal monitoring rules while strictly preserving SATYA's core execution truth invariants:

1. **Deterministic Rule Engine:** Time Agent operates strictly via policy-driven temporal evaluation rules (`TemporalMonitoringPolicy`), never hallucinating or relying on unexplainable LLM predictions.
2. **Grounding in Trusted Temporal State:** Warning signals are generated by combining read-only baseline schedules, trusted actual progress, evidence coverage gaps, and schedule projections.
3. **Core Temporal Distinctions Preserved:**
   - $\text{No Report} \neq \text{No Work}$ (Silence is an evidence gap, not confirmed absence of work).
   - $\text{No Evidence} \neq \text{No Progress}$ (Lack of evidence is an observation gap, not confirmed false progress).
   - $\text{Out-of-Sequence} \neq \text{False Report}$ (Out-of-sequence execution reflects reality; baseline sequence is not a physical constraint).
   - $\text{Forecast Delay} \neq \text{Confirmed Delay}$ (Projections are risk indicators, not static historic facts).
4. **Strict `as_of_date` Temporal Bounding:** Signals and engine state rely strictly on evidence observed on or before `as_of_date` ($t_{\text{observed}} \le t_{\text{as\_of}}$).
5. **Auditable Signal Lifecycle & Deduplication:** Every evaluation run generates structured `MonitoringEvaluationRun` and deduplicated `TemporalWarningSignal` entities keyed by `signal_key` (`{project_id}|{activity_id}|{signal_type}`). Signals transition through `ACTIVE`, `RESOLVED`, `SUPERSEDED`, and `ACKNOWLEDGED`.
6. **Zero False Positives Requirement:** Null forecasts, absent reports, or out-of-sequence work are never converted into false delay signals without satisfying exact rule preconditions.

## 2. Signal Evaluation Pipeline

```
          BASELINE SCHEDULE + TRUSTED PROGRESS + FORECASTS + EVIDENCE LEDGER
                                         │
                                         ▼
                             TIME AGENT MONITORING ENGINE
                             (as_of_date & Policy Enforced)
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
     SIGNAL EVALUATION RULES                           DEDUPLICATION & LIFECYCLE
  1. SILENT_CRITICAL_PATH_RISK                         - Generate unique signal_key
  2. OUT_OF_SEQUENCE_EXECUTION                         - Match active signals
  3. FORECAST_FINISH_SLIPPAGE                          - Resolve missing conditions
  4. EVIDENCE_COVERAGE_GAP                             - Supersede stale signals
  5. STAGNANT_IN_PROGRESS                              - Create new ACTIVE signals
  6. UNTRUSTED_CLAIM_ACCUMULATION                        │
                 │                                       ▼
                 └───────────────────────┬───────────────┘
                                         │
                                         ▼
                            MONITORING EVALUATION RUN
                             (Auditable Engine Audit)
                                         │
                                         ▼
                            TEMPORAL WARNING SIGNALS
                             (REST API & Dashboard)
```

## 3. Signal Evaluation Rules & Mathematics

### 3.1 `SILENT_CRITICAL_PATH_RISK`
- **Goal:** Detect critical path activities past their planned start date without recent trusted field reports.
- **Preconditions:**
  - Activity `is_critical == True` and progress status is `NOT_STARTED`.
  - `as_of_date > planned_start_date`.
  - Days past start ($d_{\text{past}} = \text{as\_of\_date} - \text{planned\_start\_date}$) $\ge$ `critical_path_silence_days_threshold` (default: 3 days).
  - No trusted execution events observed within the silence threshold window ($t_{\text{observed}} > \text{as\_of\_date} - d_{\text{threshold}}$).
- **Severity:** `HIGH`
- **Explicit Rationale Trace:** Distinguishes between unobserved execution (evidence gap) and actual physical delay. Reports: *"Critical activity past planned start with no trusted field reports for X days."*

### 3.2 `OUT_OF_SEQUENCE_EXECUTION`
- **Goal:** Identify activities showing actual start or progress before all mandatory predecessor activities are completed.
- **Preconditions:**
  - Target activity has progress status `IN_PROGRESS` or `COMPLETED`.
  - At least one predecessor activity (via baseline `predecessor_ids`) has actual progress status $\neq \text{COMPLETED}$.
- **Severity:** `MEDIUM`
- **Explicit Rationale Trace:** Reports: *"Activity started/progressed while predecessor X remains incomplete. Out-of-sequence execution detected in field."*

### 3.3 `FORECAST_FINISH_SLIPPAGE`
- **Goal:** Flag activities where current forecast finish date slips past planned baseline finish date beyond configured tolerance.
- **Preconditions:**
  - `ForecastStatus == ForecastStatus.AVAILABLE` (Null-forecast safe: evaluated **only** when a valid forecast exists).
  - Days slippage ($S = \text{forecast\_finish\_date} - \text{planned\_finish\_date}$) $>$ `slippage_days_threshold` (default: 5 days).
- **Severity:** `HIGH` if `is_critical == True`, else `MEDIUM`.
- **Explicit Rationale Trace:** Reports: *"Forecast finish date slips past planned finish by X days (Forecast: Y, Planned: Z)."*

### 3.4 `EVIDENCE_COVERAGE_GAP`
- **Goal:** Surface in-progress activities operating with zero trusted supporting evidence for an extended duration.
- **Preconditions:**
  - Target activity progress status is `IN_PROGRESS`.
  - `as_of_date - actual_start_date` $\ge$ `evidence_gap_days_threshold` (default: 7 days).
  - Trusted evidence count for activity $== 0$.
- **Severity:** `MEDIUM`
- **Explicit Rationale Trace:** Reports: *"Activity in progress for X days without any trusted supporting evidence."*

### 3.5 `STAGNANT_IN_PROGRESS`
- **Goal:** Detect active tasks with zero physical progress gains over a prolonged period.
- **Preconditions:**
  - Target activity progress status is `IN_PROGRESS`.
  - `physical_progress_pct < 100.0%`.
  - `as_of_date - last_trusted_event_timestamp` $\ge$ `stagnant_days_threshold` (default: 10 days).
- **Severity:** `MEDIUM`
- **Explicit Rationale Trace:** Reports: *"In-progress activity has seen no progress or updates for X days."*

### 3.6 `UNTRUSTED_CLAIM_ACCUMULATION`
- **Goal:** Highlight activities accumulating high volumes of unverified/untrusted progress claims or contradictions.
- **Preconditions:**
  - Count of untrusted/review-required events for activity $\ge$ `untrusted_claim_count_threshold` (default: 3).
- **Severity:** `HIGH`
- **Explicit Rationale Trace:** Reports: *"Accumulated N untrusted or contradicted progress claims requiring HITL reconciliation."*

## 4. Signal Lifecycle & Persistence Model

### 4.1 Persistence Schema
Temporal warning signals and evaluation run audits are persisted in SQLite:
- `monitoring_evaluation_runs`: Stores evaluation metadata (`evaluation_run_id`, `project_id`, `as_of_date`, `signals_detected_count`, `signals_active_count`, `executed_at`).
- `temporal_warning_signals`: Stores warning signal state (`signal_id`, `project_id`, `activity_id`, `signal_type`, `severity`, `status`, `signal_key`, `title`, `description`, `rationale_trace`, `first_detected_at`, `last_detected_at`, `resolved_at`, `evaluation_run_id`).

### 4.2 Deduplication & Transition Logic
- **`signal_key` Formation:** `{project_id}|{activity_id}|{signal_type}`.
- **Repeat Evaluation:** If an active signal with matching `signal_key` is detected, `last_detected_at` and `evaluation_run_id` are updated. No duplicate signal rows are inserted.
- **Automatic Resolution:** If a previously active signal is no longer triggered during an evaluation run, its status transitions to `RESOLVED` with `resolved_at = as_of_date`.
- **Manual Acknowledgment:** Planners can acknowledge signals via `POST /api/v1/monitoring/signals/{id}/acknowledge`, transitioning status to `ACKNOWLEDGED`.

## 5. API Endpoints

- `POST /api/v1/monitoring/evaluate`: Trigger Time Agent monitoring evaluation for a project.
- `GET /api/v1/monitoring/projects/{project_id}/signals`: Retrieve active temporal warning signals for a project (supports filtering by `severity` and `signal_type`).
- `GET /api/v1/monitoring/signals/{signal_id}`: Retrieve detailed breakdown and rationale trace for a specific warning signal.
