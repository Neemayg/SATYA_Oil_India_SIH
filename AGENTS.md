## 1. Project Mission

You are working on **SATYA**, an evidence-backed **Execution Truth Layer** designed for Oil India Limited as part of Smart India Hackathon 2026.

SATYA is **NOT** a generic AI chatbot or standard reporting dashboard. It is an execution intelligence layer positioned between heterogeneous field execution observations (DPRs, voice logs, inspection reports, site photos, contractor updates) and the formal L5/L6 project schedule (Primavera P6 / MS Project).

### Core Responsibilities of the System
1. Ingest raw, heterogeneous field inputs.
2. Extract structured **Execution Events** preserving complete provenance and raw content.
3. Link Execution Events to L5/L6 baseline schedule activities using **Activity Fingerprints** (semantic + structural + spatial + temporal context).
4. Validate linkages with multi-modal evidence and calculate explicit confidence scores.
5. Surface contradictions, conflicts, and evidence gaps.
6. Enable Human-in-the-Loop (HITL) calibration for low-confidence or disputed matches.
7. Produce verified, trusted actual progress and feed human corrections into **Institutional Memory** for long-term productivity and delay estimation.

## 3. Architecture Principles

1. **Evidence-Backed Truth:** Progress is never declared based on unverified text alone; every actual start/finish or progress percentage must map to verifiable execution evidence.
2. **Immutable Observation Event Ledger:** Raw inputs and extracted Execution Events are append-only. They are never overwritten, destroyed, or silently altered.
3. **Schedule-Aware Grounding:** Matching relies on structural WBS hierarchy, predecessors/successors, site location, and temporal boundaries—not just surface-level semantic text similarity.
4. **Explainable AI:** Every match, confidence score, and conflict flag generated by AI must provide human-readable reasoning trace.
5. **Human-in-the-Loop Safeguard:** AI is an analyst, not an autonomous authority. Low-confidence matches and contradictions require human planner validation before actual schedule updates occur.
6. **Institutional Memory Accumulation:** Human planner corrections and true field execution rates are captured to improve future matching accuracy and baseline planning realistic estimates.

---

## 4. Coding Principles

1. **Simplicity Over Cleverness:** Prefer plain, testable, legible logic over complex over-engineered abstractions.
2. **Strict Boundary Control:** Decouple parsing, event extraction, activity fingerprinting, matching, conflict scoring, and projection into discrete modules.
3. **No Silent Transformations:** Fail explicitly or return structured `UNMATCHED` status rather than guessing or silently coercing bad data.
4. **Deterministic Testing:** Core matching, confidence math, and conflict engines must be unit-testable without live external LLM network calls.

## 7. AI Safety Principles

1. **No Hallucinated Schedule IDs:** The AI model must NEVER invent, construct, or hallucinate a schedule `Activity ID` or `WBS ID` that does not exist in the ingested schedule baseline.
2. **Support UNMATCHED:** The matching engine must explicitly support and output `UNMATCHED` when field evidence is ambiguous, absent, or insufficient.
3. **Confidence Scoring Mandatory:** Every match must produce a normalized confidence score $[0.0, 1.0]$ backed by explicit factor breakdown (semantic, structural, temporal).
